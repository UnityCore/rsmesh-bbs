    - Goal: structured maintenance for known settings; keep sys_config as backing store
    - Known-setting screens (examples):

    - Generic advanced mode (optional):
      - Retain list/edit/delete for power users or module-added keys
      - Or move raw CRUD to a hidden "Advanced Configuration" submenu
    - Validation:
      - Type-aware editors (bool, int, string); reject invalid values before save
      - Protect required keys from delete; warn on keys with dedicated admin UI
    - config.yml round-trip:
      - Export writes known sections cleanly; seed/upgrade merges new keys on startup
      - Document which keys are operator-editable vs internal-only
    - Suggested phasing:
      - Phase A: schema/registry of known sys_config keys + typed edit forms for bbs/schedule
      - Phase B: demote or relocate raw CRUD; export/import alignment with example_config.yml
      - Phase C: module-registered config keys (if modules need sys_config exposure)

- Module sync capability (framework extension) [NOT STARTED]
    - Bulletins, Mail, and Channels remain core sync types (tc2/rsv1 wire formats unchanged)
    - Modules today: mesh menus, schedules, register_service only — no sync hooks
    - Goal: let enabled modules register optional sync participation without moving core
      services into modules (Channels stays core for 1.1)
    - Module registration (at on_load or via ModuleManager), e.g.:
      - sync_record_type id (module-owned data; may use module-local DB like node_info)
      - rsv1 wire message type(s) and encode/decode handlers (rsv1 first; tc2 optional later)
      - inbound ingest handler (called from message_processing when peer + module enabled)
      - outbound sync handler for pending records (called from sync_pending_records worker)
      - optional delete/reconcile handler if the module needs peer delete semantics
    - Gating:
      - Ignore module sync ingest when module disabled (same idea as core service off)
      - Respect sync peer flags where applicable; module may define peer flag names or use
        a generic modules sync enable on the peer row (design TBD)
    - record_sync_peers / synced status:
      - Extend or generalize beyond SYNCED_TABLES for module record types, or module
        stores sync state in its own DB with a documented contract
    - Admin tool:
      - List Unsynced Data: include module-registered types when module enabled
      - Module admin screens may show module-specific sync status
      - Status/splash counts: optional module hook to contribute lines (or query via service)
    - docs/RSMESH-BBS-DEVELOPER-GUIDE.md: document sync registration API and first reference module
    - Suggested phasing:
      - Phase A: registration API + dispatch from message_processing / sync_pending_records
      - Phase B: admin List Unsynced integration; peer flag design
      - Phase C: first module using sync (candidate: proof-of-concept module, not core Channels)
